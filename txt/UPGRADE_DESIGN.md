## 1. 现状盘点 + L1 压缩问题分析（重点）

### 1.1 当前 L1→L2 压缩流程（`memory.py`）

```
add_turn(用户, AI, 时间)
   │  写入 L1，summarized=False，立即落盘
   ▼
未总结轮数 >= l1_summary_rounds(默认10) 且后台空闲
   │  _trigger_summary()：快照「前 10 条未总结」→ compacting=True → 入队列
   ▼
后台 _loop() 线程：
   items = compressor.compress(batch)      # LLM 把 10 轮压成 1~3 条要点（纯文本）
   vecs  = [embedder.embed(t) for t]       # 逐条向量化
   store.add(items, vecs)                  # 写 L2
   finally: l1.mark_summarized(10)         # 标记这 10 条已总结
```

### 1.2 确认的问题清单（含代码位置）

### 1.3 为什么"参考 AI1"会出问题（一句话）

AI1 的压缩不是"一句话要点"，而是一套**带结构、带重要度、带访问统计、带二次压缩规划**的话题系统（`topic_file.py`）。本项目做减法时，把**最重要的「重要度 / 访问统计 / 情绪 / 结构化」全砍掉了**，只留了个"LLM 吐 1~3 条字符串"的壳，再叠加 P1 那个"失败也标记"的 bug，结果就是：**长期记忆既丢数据、又无权重、还无情绪**。

结论：**压缩引擎需要重写**（保留"10 轮一批、后台异步、快照不阻塞"这三点好设计，其余换新，见 §3/§4）。

### 1.4 P1~P4 的解决方案（✅ 已定方向）

**P1 —— 失败不标记，记忆永不丢**

- 把 `mark_summarized(len(batch))` **从 `finally` 移出**，只在「压缩 → 向量化 → 入库」三步全部成功后调用。
- 任一步失败：写日志 → `compacting=False` → **不调用 `mark_summarized`**，这批轮次保持 `unsummarized`，等下一次 `add_turn` 触发时自然重试（自带退避，不会空转刷 API）。
- embedding 原子性：改为**一次性批量** `embed(items)` 得到完整向量数组，成功后才 `store.add(items, vecs)`；中途失败则既不入库、也不标记。
- 批量 embedding 加超时与重试；若某批连续失败，只记日志、不丢数据，等 API 恢复后重试。

**P2 —— 压缩带上下文 + 相似度去重（✅ 已定）**

- `Compressor.compress()` 扩展签名为 `compress(turns, profile, existing_items)`。
- prompt 追加两段：
  1. **用户画像**（稳定事实，避免把已知事实重复抽成"新"记忆）；
  2. **已有 L2 的相关条目摘要**（供去重，或标注"这是对旧记忆的更新/推翻"）。
- **相似度去重（写库前执行，核心）**：压缩出新条目 → 先向量化 → 与已有 L2 逐条算余弦相似度：
  - `相似度 ≥ 阈值`（默认 0.85，可配）→ 判定**高度重叠**，**更新**该旧条目：合并文本、**重算重要度**、刷新 `time`/`last_accessed`，**不新增**。
  - `相似度 < 阈值` → 正常新增。
  - 这样既去重，又实现"记忆随新信息持续更新"（例如"计划做 X" → 后来"X 已做完"，旧条目被更新而不是并存两条矛盾）。
- `MemoryManager` 触发压缩时，从 `store` 取已有 L2 传入（用于去重比对）。

**P3 —— 结构化输出：要点 + 重要度 + 情绪**

- 压缩器要求 LLM 返回结构化 JSON（不再是一句字符串）：
  ```json
  [{"text": "用户计划添加工具调用能力", "importance": 4, "emotion": "平静", "emotion_value": 0.0}]
  ```
- `importance` 用 1~5 整数，入库时归一化到 0~1（§3.2）。
- 解析失败或字段缺失时用默认值（`importance=3`、`emotion="平静"`、`emotion_value=0`），**绝不因格式问题丢整批**。

**P4 —— 情绪随压缩留存**

- 同一份结构化输出里带 `emotion` / `emotion_value`，即"这段记忆的情绪基调"直接存进 L2。
- 配合 §4 情绪系统：检索时记忆的 `emotion_value` 反哺当前情绪（记忆唤起情绪）。

## 3. L2 字段扩展设计

### 3.0 L2 与画像的分工（设计原则，✅ 已定）

- **L2 的目的**：让 AI **像人一样提取记忆，在对话时有选择性**。它不是"把对话全文存下来"，而是从对话里抽出"值得长期记住的要点"，并在需要时按「相关性 × 重要度」**有选择地回忆**（而不是每次把全部 L2 都灌给模型）。
- **画像的目的**：专门承载「**能说明用户长期不变、但几乎不怎么被提起**」的内容（称呼、关系、稳定偏好、长期目标等）。这类内容因为出现频率低，容易被 L2 的近因衰减/遗忘冲淡，所以**单独常驻 system prompt，不参与衰减**。
- **分工**：L2 = 事件性/高频/需要选择性回忆的；画像 = 低频/稳定/常驻的。两者不重叠、不互相淘汰。

### 3.1 新 L2 条目结构

```jsonc
{
  "id": "l2-1750000000000-0",
  "time": "2026-08-17 周一 19:25:35",      // 生成时间（不变）
  "text": "用户计划为 AI 添加工具调用能力",     // 要点正文（不变）
  "importance": 0.72,                        // 【新】重要度 0~1
  "emotion": "平静",                          // 【新】情绪标签（离散，见 §4）
  "emotion_value": 0.1,                       // 【新】情绪效价 -1~1（负=负面）
  "source": "compress",                       // 【新】来源：compress / manual / tool
  "access_count": 0,                          // 【新】被检索命中次数
  "last_accessed": "",                        // 【新】最近命中时间
  "last_proactive_used_at": "",               // 【新】最近被"主动发消息"用作话题的时间（避免重复取同一记忆）
  "created_at": "2026-08-17 周一 19:25:35"    // 【新】创建时间（与 time 区分，用于衰减）
}
```

- **兼容旧数据**：`_load()` 读旧 `memory.json` 时，缺字段自动补默认值（`importance=0.5`、`emotion="平静"`、`emotion_value=0`、`access_count=0`），**不破坏已有向量/文本**。

### 3.2 重要度（importance）怎么算（✅ 已定）

分两层，**写入时给基值、检索时算动态值**：

**① 写入时（压缩阶段）**：让 LLM（分析模型）在压缩的同时给每条要点打一个 `importance ∈ {1..5}`，归一化到 0~1 存进 `importance`（作为基值 `base_importance`）。这样"用户妈妈的生日"会比"今天吃了外卖"分高。

**② 检索时（动态重要度）**，参考 AI1 `topic_file.py` 的「访问频率分 + 近因分」思路：

```
freq_score    = min(1, log1p(access_count / 存活天数) / log1p(20))   # 访问频率分（AI1 同款）
recency_score = exp(-距今未访问天数 × ln(2) / 14)                     # 近因分，半衰期 14 天 ✅
动态重要度 = base_importance × (0.6 × freq_score + 0.4 × recency_score)
```

- **半衰期 14 天 ✅ 已定**。
- **权重参考 AI1**（AI1 是 freq:0.5、recency:0.35，归一化后约 0.6 / 0.4）。⚠️ 注意：AI1 的 `importance` 公式里还叠了一个**废弃的 L3 项**（`layers × 0.5`，且代码里用 `Compression_layers` 键、注释里用 `compression_layer`，键名对不上，实际是失效的），所以**AI1 的权重并不完全可靠**；本设计只取其 freq/recency 的相对比例、**去掉 layers 项**，并把两个系数做成可配置参数，联调时标定。
- 主动发消息选话题时，也用这个 `动态重要度` 排序（§6.4）。

**③ 检索排序**：`score = 0.7×余弦相似度 + 0.3×动态重要度`（权重可配置）。这样既相关、又重要、又较新近的记忆排在前面。

### 3.3 情绪字段（emotion / emotion_value）

- `emotion`：离散标签，如 `平静 / 开心 / 兴奋 / 难过 / 生气 / 焦虑 / 害羞`（集合可配）。
- `emotion_value`：连续效价 -1~1（负=负面情绪，正=正面情绪），供情绪系统做数值计算（§4）。两条同时存：`emotion` 给人看/给模型看，`emotion_value` 给算法算。

**✅ 已定 3.1**：`emotion` 离散标签 + `emotion_value` 连续效价**两者都要**——标签给模型看（写进 prompt 更直观），数值给算法算（§4 的情绪结算）。

## 4. 情绪系统 + 动态温度（重点）

### 4.1 思路来源（✅ 情绪状态模型以 B 站灵梦桌宠评论思路为主）

情绪状态模型**以 B 站灵梦桌宠视频评论区的思路为主线**，落到本项目就是三条：

> 1. 让 AI 有一个**持久化的情绪状态**，用算法从"上下文 + 检索到的记忆"推算出"当前大致情绪"；
> 2. 把这个情绪映射成**下一次说话的 temperature**（情绪决定说话风格）；
> 3. **检索 L2 记忆时也算出这些记忆会唤起什么情绪**，反哺当前情绪（情绪一致性记忆，mood-congruent memory）。

§4.2~§4.5 全部围绕这三条展开：持久情绪态 → 每轮情绪结算 → 情绪→温度映射 → 记忆情绪反哺。

### 4.2 情绪状态模型（持久化）

每个 `(user_id, role_name)` 一份，存 `data/emotion/<user>/<role>.json`：

```jsonc
{
  "emotion": "平静",     // 当前情绪标签
  "valence": 0.0,        // 效价 -1~1
  "arousal": 0.3,        // 唤醒度 0~1（平静~激动）
  "updated_at": "2026-08-17 周一 19:25:35"
}
```

采用**二维情绪模型**（心理学常用的 valence–arousal），既够用又简单：
- **valence（效价）**：-1 负面 ~ +1 正面，决定"开心还是难过"。
- **arousal（唤醒度）**：0 平静 ~ 1 激动，决定"冷静还是兴奋/愤怒"。
- `emotion` 标签由 `(valence, arousal)` 映射而来（例如：高 arousal 正效价→兴奋，高 arousal 负效价→生气，低 arousal 正效价→满足，低 arousal 负效价→低落）。

> ✅ **情绪指 AI 自己可能的情绪**（不是用户情绪）：由当前上下文（用户说了什么 + AI 刚才回了什么 + 检索到的记忆情绪）**推断**出来。L2 里的 `emotion`/`emotion_value` 记录的也是"AI 当时在这段对话里的情绪基调"。

### 4.3 每轮情绪结算管线（核心）

```
用户发来消息
  │
  ① 检索 L2 top-K（含 emotion / emotion_value）
  │     → 记忆唤起情绪 = Σ(emotion_value_i × 相似度权重) / Σ权重   ← "检索时也算情绪"
  │
  ② 情绪更新 = 自然衰减(上一轮) + 记忆唤起情绪×0.3 + 用户消息情绪×0.7
  │     自然衰减：valence/arousal 每轮向 0 回缩一点（如 ×0.85），情绪不会一直亢奋
  │
  ③ 动态温度 = f(valence, arousal)    ← "情绪决定下一次说话温度"
  │
  ④ 组装 system（人设 + 时间 + 画像 + 记忆 + 【当前情绪提示】）
  │     → 调 AI，temperature = 动态温度
  │
  ⑤ AI 回复后：用一次轻量 LLM 抽取"这句回复体现的情绪"
  │     → 更新持久化情绪态（供下一轮用）
```

### 4.4 情绪 → 温度映射（✅ 已定：配置温度与情绪温度取平均）

核心直觉：**唤醒度（arousal）主要驱动温度，效价（valence）做微调**。

```
情绪温度 T_emotion = clamp( T_base + (arousal - 0.5) × 2 × T_span + 效价微调 , T_min, T_max )
                      其中 效价微调：负面且高唤醒（生气）+δ，正面且低唤醒（平静满足）−δ

最终调用温度 T = ( T_base + T_emotion ) / 2     ← ✅ 已定：配置文件温度 与 AI 情绪温度 各占一半
```

| 情绪 | valence | arousal | 大致温度方向 |
|---|---|---|---|
| 平静 / 满足 | ~0~+ | 低 | 偏低（稳定、温柔） |
| 开心 / 兴奋 | + | 高 | 偏高（活泼、有变化） |
| 生气 / 焦虑 | − | 高 | 偏高（情绪化、语气强） |
| 低落 / 难过 | − | 低 | 偏低（寡言、低沉） |

- `T_base` 仍取 `text_model_information.temperature`（保留用户现有配置）。
- 新增配置 `emotion_information`：`enabled`、`temperature_span`（情绪摆动幅度，默认 0.3）、`temperature_min/max`、`decay`（每轮衰减系数）、`inject_emotion`（是否把情绪写进 prompt）。
- 温度最终只影响**对话模型**调用；分析模型（情绪抽取/压缩/搜索决策）始终用低温度（0.1）保证稳定。

### 4.5 情绪的抽取方式（✅ 已定）

| 方案 | 做法 | 成本 | 精度 |
|---|---|---|---|
| A（推荐） | 每轮回复后，用**轻量 LLM** 抽一次 `{valence, arousal, emotion}`，返回 JSON | 每轮多 1 次小调用 | 高 |
| B | 用规则/情感词典粗算（无 LLM） | 0 额外成本 | 低、中文语气易误判 |

> 抽取时用**分析模型**（`analysis_model_information`，见 §4.6），temperature 设低（如 0.1）保证抽取稳定。

**✅ 已定 4.1**：情绪抽取用**方案 A（LLM 抽取，用分析模型）**。每轮回复后调一次分析模型抽 `{valence, arousal, emotion}`。为控制成本，后续可加"每 N 轮抽一次 + 中间轮纯衰减"的优化开关，但第一版先每轮抽。

**✅ 已定 4.2**：温度映射用**线性公式**（§4.4），最终调用温度 =（配置温度 + 情绪温度）/ 2，`T_span/T_min/T_max` 全部可配置。

### 4.6 分析模型（analysis_model_information，✅ 已定）

新增一个独立于对话模型的**分析模型**配置（参考 AI2 `prepare_file.py` 的 `analysis_model_information`），专用于"分析类"任务，temperature 低（0.1）保证输出稳定、JSON 可解析：

```jsonc
"analysis_model_information": {
  "name": "deepseek-v4-flash",
  "apikey": "",                              // 优先环境变量，同现有密钥策略
  "base_url": "https://api.deepseek.com",
  "temperature": 0.1,
  "output_format": "json"                    // 分析结果一律 JSON，便于代码解析
}
```

| 用途 | 谁在用 |
|---|---|
| **情绪/温度分析** | §4.5 每轮抽取 AI 情绪 `{valence, arousal, emotion}` |
| **文本压缩** | §1.4 P3 压缩器：从对话提炼要点 + 重要度 + 情绪 |
| **网络搜索决策** | §5.5 判断"这条消息是否需要联网搜索" |

- **Streamlit 上允许用户自定义**：模型名 / apikey / base_url / temperature 全部可编辑（密钥脱敏，可改后保存，热切换）。
- 与 `text_model`（对话）、`embedding_model`（向量）三者分离，互不影响。
- 默认值与 `text_model` 相同（`deepseek-v4-flash`），用户可换成更便宜/更快的模型省钱。

## 5. 工具调用

### 5.1 目标

- 新增一个文件夹（建议 `tools/`），AI 需要的工具都放里面。
- AI 在对话中能**按需调用**这些工具（OpenAI 兼容的 function calling）。
- **安全工具白名单**：默认提供一批**已经审核过的安全工具**（`web_search`、计算器、时间查询等），每条工具带 `safe` 标记，AI 被明确告知"这是安全工具"。
- AI 还能**执行自己生成的代码**（临时/持久工具）——这是风险最高的一项，**默认关闭**，需在 Streamlit 上显式开启（见 §5.4）。

### 5.2 目录与工具格式

```
wechat-ai-bot/
└── tools/
    ├── web_search.py      # 【内置】网络搜索（配合 §5.5 的搜索决策）
    ├── 计算器.py           # 用户手写的工具
    ├── 时间查询.py
    └── manifest.json      # （可选）工具注册表，也可靠自动扫描
```

每个工具文件一个约定结构（自动发现）：

```python
# tools/计算器.py
TOOL = {
    "name": "calculate",
    "description": "计算一个数学表达式，返回数值结果。",
    "safe": true,                        # 【白名单标记】true = 已审核的安全工具，AI 可直接用
    "parameters": {                      # OpenAI function-calling 的 JSON Schema
        "type": "object",
        "properties": {"expr": {"type": "string", "description": "数学表达式，如 '3*4+2'"}},
        "required": ["expr"],
    },
}

def run(expr: str) -> str:
    return str(eval(expr, {"__builtins__": {}}, {}))   # 极简安全示例，实际要更严格
```

- 启动时扫描 `tools/*.py`，读 `TOOL` + `run`，注册进工具表；`web_ui` 里可查看/增删/启停工具。
- **白名单机制**：`safe=true` 的工具进「安全白名单」，system prompt / tools 描述里明确标注为安全工具，AI 无需额外授权即可调用；`safe=false` 或未标记的工具按"非白名单"处理。
- `ai_client` 扩展：`complete()` 支持传 `tools`，收到 `tool_calls` 后执行工具、把结果回填再问一轮，循环直到出最终文本（或达最大轮数防死循环）。

### 5.3 AI 自生成代码（工具即代码）

AI 想用一个不存在的工具时，可以**现场生成 Python 代码**：

```
AI 回复里出现 <tool>...代码...</tool> 或 function-calling 请求一个"自生成工具"
   │
   ▼
tool_kit 校验 → 写入 tools/_generated/<hash>.py → 在沙箱执行 → 结果回填
```

- **持久 vs 临时**：一次性脚本存 `tools/_generated/`，可配置"执行后保留"或"自动清理"。
- **危险**：任意代码执行 = 任意删文件/联网/拖库。所以必须沙箱（§5.4）。

### 5.4 执行安全（✅ 已定：折中方案）

安全级别分三档，**最终采用折中方案（L0 默认 + 白名单 + 生成代码开关）**：

| 级别 | 方案 | 说明 |
|---|---|---|
| L0 白名单 | 只允许运行 `tools/` 里 `safe=true` 的**白名单安全工具**；AI 自生成代码**默认关闭** | 默认状态 |
| L1 受限执行 | AI 自生成代码在**受限沙箱**跑：`subprocess` + 超时 + 只读工作目录 + 禁网 + 禁危险模块 | 用户主动开启后启用 |
| L2 完全自由 | 任意执行（等同本机用户权限） | **不做，强烈不建议** |

**✅ 已定 5.1**：采用**折中方案**——
1. **默认状态（安全）**：AI 只能用 `safe=true` 的**白名单安全工具**（web_search、计算器、时间查询等）；**AI 自生成代码能力默认关闭**。
2. **白名单告诉 AI 哪些是安全的**：tools 描述里带 `safe` 标记，AI 明确知道"这是安全工具，可以放心用"。
3. **Streamlit 加一个「允许 AI 生成并执行代码」开关**（默认**关闭**）：只有用户手动打开后，AI 才具备现场生成代码的能力。
4. **开启时红字警告**：打开该开关的瞬间，页面上以**红色大字**警告——"⚠️ 开启后 AI 可生成并执行代码，可能产生不可预期的严重后果（如误删文件、执行恶意操作），请确保你信任该 AI 并知晓风险"。用户确认后才生效。
5. 开启后，AI 生成的代码仍在 **L1 沙箱**执行（超时、只读临时目录、禁网、禁 `os.system/subprocess/socket` 等危险模块）。
6. 每次自生成代码执行前，在日志里留**完整代码快照**，便于追溯。

**✅ 已定 5.2**：工具目录用 `tools/`，自动扫描注册 + `web_ui` 里可查看/增删/启停（含 `safe` 标记编辑）。

### 5.5 网络搜索能力（✅ 已定）

- `tools/` 内置一个 `web_search` 工具（搜索引擎可用可配置的搜索 API，或 DuckDuckGo 等）。
- **是否搜索由分析模型先判断**（§4.6）：用户消息进来后，先让分析模型判断"这问题是否需要联网"（返回 `{"need_search": true/false}`）：
  - `need_search=true` → 在 tools 列表里**启用** `web_search`，让对话模型按需调用；
  - `need_search=false` → 不启用，省一次搜索调用、也避免无关联网。
- 搜索结果是工具返回值，回填进对话，再由对话模型组织成自然回复。

## 6. 主动对话

`DESIGN.md` 已经规划过（阶段二~四），这里落成具体设计。

### 6.1 能力清单（✅ 已定范围）

1. **定时主动发**：如每天 8:00 说早安（`scheduler.py` 定时触发）。
2. **提醒解析**：用户说"提醒我明天 9 点开会" → LLM 解析出 `{时间, 内容}` → 到点主动发。
3. **周期性主动消息**（本次新增确认）：每隔固定间隔（如 2~3 小时）主动发一条消息，内容由 AI 结合当前上下文/画像/情绪现场生成。
   - **间隔可自定义**：`proactive_information.interval_hours` 配置（默认 3 小时，可设 0 表示关闭）。
   - **发送时间可自定义**：可配置"只在指定时间段内主动发"（如 8:00~23:00），避免半夜打扰。
   - **Streamlit 加按钮**：主动模式的**开关**、**间隔/时间段设置**、以及一个**「立即主动发一条」手动触发按钮**（方便测试）。
4. **智能主动**（后置/可选）：闲时根据画像/记忆判断"要不要主动搭话"（如久未联系、有未完成计划）——本版先不做，架构上预留钩子。

### 6.2 新增模块

| 模块 | 职责 |
|---|---|
| `state.py` | 持久化 bot 身份 + 最近 `context_token` + 上次活跃时间，重启不丢 |
| `scheduler.py` | 独立后台线程，轮询提醒/定时任务，到点走 `service` 生成一句主动消息并发送 |

### 6.3 关键约束（务必记住）

`DESIGN.md` §4 已写清，主动对话受 iLink 限制：
- **`context_token` 只能从"对方发来的消息"里拿到**，所以首次主动前，对方必须**先发过至少一条**。
- token 会过期（社区报 `ret=-2`），过期后需对方再发一条。
- 登录会话约 24h，重扫码身份 ID 会变。

所以主动对话是"**机会式**"的：发前检查 token 新鲜度，过期则本轮跳过/降级为"记录提醒、等对方下次发消息时再补发"。`state.py` 必须把 token + 时间戳落盘，重启恢复。

### 6.4 话题选择 + 与情绪/温度的关系（✅ 已定）

**① 话题选择（从高重要度记忆取，且避免重复）**

- 主动消息的**话头**从 L2 里选：按 §3.2 的 `动态重要度` 排序，**取重要度高的一条记忆**作为切入点（例如"你上次说的那个项目进展如何"）。
- **避免重复取同一条**：L2 每条带 `last_proactive_used_at`（§3.1）。取话题时**优先取「动态重要度高 且 `last_proactive_used_at` 最久远」**的；选中后把该条的 `last_proactive_used_at` 更新为当前时间。这样连续多次主动发消息会自动轮换话题，不重复唠叨同一件事。
- 兜底：若 L2 为空或全部近期刚用过，则退化为"通用问候"（早安/在吗/关心近况），由当前时间 + 画像 + 情绪临时生成。

**② 与情绪/温度的关系**

- 主动消息同样走 §4 的情绪结算：**主动说话也用当前情绪决定温度**。
- 内容生成复用 `service` 的新入口 `proactive_once(role, user_id)`：以「选中的高重要度记忆 + 当前时间 + 画像 + 当前情绪」为输入，让对话模型围绕该记忆起一个自然的话头。
- 生成后：按 `|||` 分段发送（若有）、写进 L1（作为一轮 AI 独白）、更新情绪态与 `last_proactive_used_at`，与普通对话一致。

## 9. 验证方式（先行列出，便于讨论时对齐）

| 能力 | 验证 |
|---|---|
| P1 修复 | 人为断网让压缩失败 → 未总结轮数**不减**，网络恢复后能重试 |
| L2 字段 | 聊 10 轮 → 看 `memory.json` 每条有 `importance/emotion/emotion_value`；旧数据不崩 |
| 相似度去重 | 反复聊同一件事 → L2 不新增重复条目，旧条目被更新且重要度重算 |
| 动态温度 | 说让它开心/激怒它 → 观察下一条回复的随机性/语气变化；日志打印实际 temperature（=配置与情绪的平均） |
| 情绪结算 | 连续聊"开心话题"后情绪态 valence 升高；隔一段时间不动，情绪自然回落（情绪是 AI 自己的） |
| 分析模型 | 网页里改分析模型名/key/temperature → 情绪抽取/压缩/搜索决策用新配置，热切换生效 |
| 工具调用 | 配一个"计算器"工具 → 问"3*4+2 等于几" → AI 调工具回"14" |
| 网络搜索 | 问"今天天气" → 分析模型判 need_search=true → 调 `web_search`；问"3+5" → 判 false 不搜索 |
| 自生成代码 | 开启开关后，问一个工具库没有的能力 → AI 生成代码在沙箱执行并回结果（沙箱外无副作用）；关闭开关时 AI 不生成代码 |
| 白名单 + 警告 | 关闭开关时 AI 只用 `safe=true` 工具；打开开关瞬间网页出现**红字警告**，确认后才生效 |
| 主动对话 | 设"1 分钟后提醒" → 到点收到（对方先发过一条消息的前提下）；连续多次主动 → 话题不重复 |
