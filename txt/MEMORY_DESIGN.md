## 0. 一句话总结

AI 分身三层记忆:**L1 短期原文**、**L2 长期要点(向量化,按需检索)**、**用户画像(常驻提示词)**,外加"分段模拟打字"和"Streamlit 管理界面"两个配套设施。

---

## 1. 三层记忆总览

| 层 | 是什么 | 存哪里 | 生命周期 | 进 prompt 方式 |
|---|---|---|---|---|
| **L1** 短期 | 最近约 10 条原始对话 | 内存(可选落盘) | 滚动窗口 | **全部**拼接 |
| **L2** 长期 | 从 L1 压缩出的要点(一条=一个事实/事件) | 文本进 json + **向量进二进制文件** | 长期累积 | **余弦相似度检索 top-5** |
| **画像** | 稳定事实/偏好/性格/称呼/关系/近期事项 | 磁盘 json | 长期,增量更新 | **常驻 system prompt** |

---

## 2. 数据流转(L2 压缩不中断版)

```
每轮对话 → 追加到 L1(一个"活列表",先不淘汰)
     │
     │ 当 L1 满 10 条,且后台空闲时:
     ▼
快照这 10 条 → 交给后台线程压缩(标记"压缩中")
     │         ├─ 新到的第 11、12 轮继续追加到活列表,绝不丢失
     │         └─ 压缩完成、L2 写盘后,才把这 10 条从活列表移除
     ▼
新 L2 → 向量化(阿里云 text-embedding-v4, 1024 维) → 存库
     │
     ▼
触发画像增量更新(见 5.2)
```

**关键点:压缩期间不淘汰任何 L1**,第 11 轮到来时先缓存在活列表里,等压缩提交后再清理已压缩的 10 条。这样永远不会出现"第 11 轮记忆中断"。

实现上就是一个"快照 + 提交后清理"的模型,不需要锁,一个后台线程 + 一个队列即可。

---

## 3. 向量检索

```
新消息 → embedding(text-embedding-v4, 1024维) → 和库中所有 L2 向量算余弦相似度
       → 取 top-5 → 拼进 prompt 的"相关记忆"段落
```

- 相似度 = 余弦相似度(numpy 手写)
- K = 5(已定)

---

## 4. 向量存储压缩(回答"一条向量 22KB"的问题)

你说得对,把 1024 个浮点数直接存 json,一条要 22KB,几千条就是几十 MB,又慢又占地方。**方案:文本和向量分开存。**

| 内容 | 存哪 | 格式 |
|---|---|---|
| 元数据(id、时间、摘要文本、来源) | `memory.json` | 纯文本,小 |
| 向量 | `vectors.npy`(并行文件) | numpy **float16** 二进制 |

- 向量先**归一化到单位长度**(反正余弦相似度要用),值都落在 [-1,1]
- 存成 **float16**:1024 × 2 字节 = **2KB/条**,比 json 文本(22KB)小约 11 倍
- 精度:float16 有 3~4 位有效数字,对余弦检索**完全够用**,不影响命中质量
- 读写用 `numpy.save / np.load(mmap_mode="r")`,10000 条才 20MB,内存也友好

> 兜底:如果以后还想更小,可降到 int8 量化(1KB/条),但第一版 float16 是"质量/体积"的最佳平衡点,先不引入量化复杂度。

## 5. 画像

### 5.1 字段(已加称呼/关系)

```json
{
  "称呼": "阿伟",              // 用户希望 AI 怎么称呼他
  "关系": "你的主人/朋友",      // 用户与 AI 的关系
  "facts":   ["职业:Python 程序员", "住在北京"],
  "prefs":   ["回复要简洁", "讨厌香菜"],
  "traits":  ["理性、计划性强"],
  "events":  ["2025-01-05 面试"],
  "updated_at": "2025-01-02T10:00:00"
}
```

### 5.2 更新频率(修正版)

| 时机 | 规则 |
|---|---|
| **首次画像** | 攒到 2 条 L2(约 20 轮)就提取第一版 |
| **之后** | 每新增 1~2 条 L2 增量更新一次(diff 合并,不全量重写) |
| **省钱开关** | 更新前让 LLM 判断"有没有新信息",没有就跳过 |

## 6. 分段回复 + 模拟真人打字

### 6.1 机制

- 提示词里告诉 AI:**如果回复较长,用 `|||` 把内容分成 2~4 段**,每段是完整自然的断句,段内不要出现 `|||`
- 机器人收到回复后按 `|||` 切分,最多 4 段,去掉空段
- **逐段发送**,段与段之间模拟真人打字停顿:

```
delay = clamp(1.0 + len(段) / 8, 1.5, 4.0) 秒
```

- 每段前后配合 `sendtyping`(正在输入 / 取消)

### 6.2 收益与风险

- **收益**:长回复更像真人一条条发,体验自然;停顿期正好给后台压缩腾出时间
- **风险(需真机验证)**:分段 = 连续多次 `sendmessage`,`context_token` 能否复用要实测
- **兜底**:多段发送失败 → 自动降级为"发送前模拟一段停顿 + 单条完整回复"


## 8. 配置格式(沿用你 prepare_file.py 的约定)

参考你之前的 `prepare_file.py`,配置也按"系统配置 / 角色配置"分开、字段用 `name/apikey/base_url` 风格:

```jsonc
// config/系统配置文件.json
{
  "text_model_information": {
    "name": "deepseek-v4-flash",
    "apikey": "<DeepSeek Key>",
    "base_url": "https://api.deepseek.com",
    "temperature": 0.7,
    "max_tokens": 1024,
    "top_p": 1.0,
    "timeout": 60
  },
  "embedding_model_information": {
    "name": "text-embedding-v4",
    "apikey": "<从环境变量 DASHSCOPE_API_KEY 读取>",
    "base_url": "https://dashscope.aliyuncs.com/compatible-mode/v1",
    "embedding_dimensions": 1024
  },
  "memory_information": {
    "enabled": true,
    "l1_window": 10,
    "l2_top_k": 5,
    "vector_store_path": "data/vector_store"
  },
  "system_information": {
    "version": "0.2.0",
    "language": "zh-CN",
    "log_level": "INFO",
    "segmented_reply": true,
    "segment_separator": "|||"
  }
}

// config/角色配置文件.json
[{
  "name": "小号AI",
  "prompt": "<人设提示词>",
  "称呼": "阿伟",
  "关系": "你的主人"
}]
```

> 说明:embedding 的 key 沿用你 prepare_file.py 的做法,运行时从 `os.environ["DASHSCOPE_API_KEY"]` 读(你已设在系统环境变量里,我实测可用)。
